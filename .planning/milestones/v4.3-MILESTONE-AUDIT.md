## 2. The Phase 43 writer-CPU gate was NOT met

This is the most important correction in this document.

| | Value |
|---|---|
| **Required** (PERF-04) | Writer CPU reduction **≥ 50%** vs legacy DuckDB baseline |
| **Measured** | **−14.4%** (lake **18.78 s** per 1M ticks vs in-memory DuckDB **16.42 s** per 1M ticks) |
| **Machine-readable record** | `reports/benchmarks/pass2_qualification_report.json` → `"overall_passed": false` |
| **Verdict** | **FAIL** |

**What went wrong in the paperwork.** Three documents assert otherwise:

1. `.planning/milestones/v4.3-REQUIREMENTS.md` marks **PERF-04 `[x]` Complete**, with the note *"final qualification evaluated and passed in Pass 2."* It did not pass.
2. `.planning/milestones/v4.3-REQUIREMENTS.md` traceability table records **PERF-04 = Complete**.
3. `.planning/milestones/v4.3-phases/43/VERIFICATION_PASS2.md` relabels the failed gate as an **"Informational comparison"**, downgrading a mandatory requirement to a note.

Each of those files now carries an appended correction block pointing here. **The machine-readable report is authoritative.** The gate is recorded as a **measured characterization, not a qualification pass**.

**Is the shortfall real or a measurement artefact?** Real. Partitioned Parquet writes fan out across many small files, each incurring its own footer, directory sync and metadata cost. Phase 41 compaction reduced file count by 56.72% and improved the ratio, but did not close the gap. This is a structural property of the chosen storage design, not a bad measurement — and it is a fair price for lock-free concurrent reads.

**Also not re-run:** PERF-01 requires qualification at **1M and 10M rows**. Both Pass 1 and Pass 2 executed at **200,000 rows**. The only 1M/10M artifacts in `.planning/artifacts/` are pre-remediation runs (10 symbols, 2-CPU host) that finding C43-05 had already flagged as defective. The scale claim is therefore **unproven at the required scale**.

## 3. What phases 37–43 did deliver

- **Phase 37** — Fail-closed release-report validator with table-driven mutation tests; isolated run directories outside tracked artifacts; production write guards rejecting symlink aliases.
- **Phase 38** — Migration source-coverage ledger making overlapping re-runs idempotent (resolving the v4.2 duplicate-partition defect C43-01); provenance-scoped publication verification (resolving C43-02 without xfail); whole-lake inventory audit; coordinator cutover/rollback rehearsal.
- **Phase 39** — Reader fail-fast with structured exceptions and **zero silent legacy fallback**; barrier-controlled snapshot race proving DuckDB raises rather than returning partial results; subprocess-isolated portable reader contract.
- **Phase 40** — Real OS SIGINT/SIGTERM lifecycle tests; crash matrix across seven persistence barriers; provider gap ledger recording explicit visible gaps with `LOSS_UNKNOWN` where loss is unquantifiable; RAM-only loss boundary documented and signed.
- **Phase 41** — Capacity monitoring with rate-limited alerting; offline compaction under a durable maintenance journal with consumer drain, multiset equivalence verification and immutable lineage; fenced physical purge with crash-safe recovery.
- **Phase 42** — Deterministic bounded replay iterator over frozen file inventories, with cursor resumption across fresh processes.
- **Phase 43** — Corrected benchmark harness: continuous peak RSS/CPU sampling replacing point-in-time snapshots; real receive-to-visible freshness measured through the actual runner and an independent reader process.

**Test suite at close:** ~1,045 passing offline tests, 0 failures, 0 xfails.

## 4. Known limitations carried forward (accepted, not hidden)

| Limitation | Consequence |
|---|---|
| Writer-CPU gate unmet (−14.4%) | Parquet writes cost more CPU than the DuckDB baseline. Accepted as the price of lock-free concurrency. |
| Qualification ran at 200k, not 1M/10M | Performance at production scale is **unproven**, though query behaviour is characterised. |
| Maintenance recovery is manual | A crash mid-compaction leaves `_maintenance/in_progress.json`; the streamer refuses to publish until `recover_maintenance` runs. Mitigated by v5.0 Phase 51 scheduling compaction in a closed window. |
| Performance suite excluded from CI | `-m 'not live and not performance'` means qualification gates never run automatically. |
| RAM-only durability window | Ticks accepted but unflushed are lost on a hard kill. Documented boundary, not a defect. |
| 8 frontend tests silently skip without Node.js | Frontend assertions may not execute in some environments. |
